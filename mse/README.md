# `:mse`

Module detail for the one-line summary in the root [`AGENTS.md`](../AGENTS.md) — read this before working inside the module.

C Media Source host for the JS YouTube player. **Not** a Kotlin `MsePlayer` / MediaCodec path.

- **JS YouTube path** — leftover + ffmpeg demux + clock live in C (`mse_ffmpeg.c` / `mse_host.c`). QuickJS `__mse*` trampolines call that C directly. **JNI has one media call: the video target** (`setVideoSurface` on Android, `bindPresenter` on desktop). Seek is JS (`seekTo` → `HTMLMediaElement.currentTime` → `__mseSetCurrentTime`), not a host export. C→JS events: `MseJsEventBridge.fire` (any thread) → `DynamicEngine.fire` → `"event"` pipe → `ymix.onEvent`. Critical C lines (starve, park/recover, ffmpeg errors) hop `mse_set_log_callback` → `MseLogBridge.fire` → `Logger.fork("mse")` (file + Sentry). Chatty `vlog`/`mse_logf` emit DEBUG; `-Pproduction=true` compiles them to `((void)0)` so format args are not evaluated. `mse_critf` INFO/WARN/ERROR always emit.
- **JVM desktop** — that C host, presenting through the desktop presenter below. Host JDK headers plus `ffmpeg-build/out/<desktop-slug>` shared libav (`FFMPEG_ROOT`) to build `libmseffmpegjni`. Same DSOs the packed `ffmpeg` CLI loads. Local files use a **separate** in-process host (`file_av.c` / `FileAvNative`), not leftover. **Linux**: audio is `aq_pulse.c` (AudioQueue subset on dlopen'd libpulse-simple); GPU decode is `mse_hwdev.c` — one process-wide CUDA (NVDEC), else Vulkan-video device for H.264/HEVC/VP9/AV1 in both hosts, frames downloaded to NV12 for the swscale blit; a codec the GPU rejects (AV1 on Pascal) falls back to software for the process. `YMUSIC_HWDEC=none|cuda|vulkan` overrides.
- **Audio clock (Android sink, AudioQueue on Apple, Pulse shim on Linux)** — media time = `seek_base` + device frames played, where `seek_base` is the first PCM's own pts after every flush; a rate change queues a checkpoint so audio already stretched at the old rate counts at it; after a flush the clock waits (≤ 2 s) for the device to start, and the wall → device handover never steps back by more than queue latency; once a shorter audio track has ended the clock plays the video out on wall time; an AudioQueue that stops calling back for 1 s is reopened.
- **Android** — same C host; app passes a `Surface` (TextureView) into C. NDK build needs `FFMPEG_ROOT` (shared libav per ABI). Audio: the C decode loop fills a PCM ring that `MseAudioOutput` (a Looper thread per host) drains into Media3's `DefaultAudioSink` through `mse_host_dac_poll`/`_report`; the sink's playout position drives the A/V clock. Its AudioTrack is small (100–200 ms); a streaming track starts only once full, so until the first playout report the host decodes as far as ring + sink take, then `0.35 s + track buffer` of output time past the clock. Video is `AMediaCodec` into that Surface (HW if the SoC has it, Google software codec otherwise). libav + CPU blit is only if MediaCodec configure/start fails. Software volume/EQ/bass/virtualizer live in `audio_fx.c` on the PCM fill path; ExoPlayer local files JNI the same DSP via `AudioFxNative`. The sink's audio session id is `MseVideoSurface.audioSessionId()`, for system audio-effect apps.
- **Apple** — the same C in this module (`libmsehost.a` + cinterop) when `ffmpeg-build/out/ios-*` exists. `bindNativeMse` is `MseHostNative.create()` + `vtable()` into QuickJS, like JVM/Android. The app deploys to iOS 15 while `libmsehost.a` compiles for iOS 12 with `-w`, which hides `-Wunguarded-availability`: an Apple API newer than iOS 15 goes behind `__builtin_available` with a working fallback (the VP9 supplemental decoder is iOS 26.2, the decoder-spec hardware key iOS 17, `VTPixelTransferSession` iOS 16).

## Desktop presentation (`vpresent*.c`)

- **One presenter per Canvas.** `DesktopVideoSurface` (jvmMain) owns the window's video `Canvas` and creates its `VPresenter` through `VideoPresenterNative` (`vpresent_jni.c`). Kinds: **D3D11** (Windows: a swapchain on the Canvas HWND; D3D11 frames zero-copy, NV12 / I420 uploaded, other formats converted to BGRA and uploaded; YUV matrix and range from the stream), **VT** (macOS: an `AVSampleBufferDisplayLayer` in an NSView over the JAWT Canvas; iOS wraps the Kotlin-owned layer the same way and never releases it), **CPU** (Linux, a failed GPU create, `cpuOnly` surfaces: swscale or the VT blit to BGRA, fitted to `setSize`, never upscaled).
- **Engines bind, never own.** Each engine registers a binder; the surface binds the presenter to the active one (`LOCAL` while the local player claims it, else `MSE`) and unbinds the other. A show under any other bind token is `VP_DROPPED`; a different engine binding flushes the picture to black.
- **Present mode = who paints the Canvas**, not hardware vs software decode: GPU at create; CPU when the GPU create fails, the D3D11 device is lost (every D3D11 presenter drops its swapchain) or the overlay view cannot be installed; NONE once detached. `VpSink.on_mode` → `PresenterSink.onPresentMode` → `DesktopVideoSurface.mode` → the panel's `setHardware(mode == GPU)`. CPU frames come only in CPU mode: `on_frame` (under `present_mu`) → `onFrame` copies into a triple-buffered `BufferedImage` → `onCpuFrame`. `snapshot()` reads the picture back in CPU mode and from a VT layer; a D3D11 presenter has none.

## Video decode (`vpipe.c`, `vpipe_hw_*.c`)

Both desktop engines decode video through a `VPipe`, which picks the decoder, falls back and reopens, and shows frames on the bound presenter. MSE uses it for every codec it does not decode itself (Apple: H.264 and VP9 on its own `VTDecompressionSession`, `mse_vt_dec.m`; Android: `AMediaCodec`, vpipe only if that fails).

- **Choice** — the platform backend (`VpHw`) when `usable()` takes the stream, the codec is not latched, and the presenter draws the backend's frames zero-copy or the backend can read them back; else software: VP9 `libvpx-vp9`, or native `vp9` for profiles 2 / 3 (the bundled libvpx has no high bit depth) and when libvpx is missing, VP8 `libvpx`, AV1 `libdav1d` (native `av1` only carries a hwaccel), others ffmpeg's default. Containers seldom state the VP9 profile: MSE reads it from the keyframe it opens at, and vpipe from every VP9 keyframe it feeds, reopening at that keyframe (no latch) when the decoder in use no longer fits it. Every open logs `vpipe open <tag> <decoder> hw=… reason=… threads=…` at INFO.
- **Backends** — Windows `d3d11va` (8-bit H.264 / HEVC / VP9 / AV1 the GPU decodes; no readback, so only under a D3D11 presenter in GPU mode — a CPU-mode surface decodes in software). Linux CUDA / Vulkan (`mse_hwdev.c`, read back to NV12). Apple `videotoolbox`: the ffmpeg hwaccel for H.264 / HEVC / AV1 (AV1 only where VT decodes it in hardware: M3 / A17 Pro and later), and a **session** decoder for 8-bit 4:2:0 VP9 on Apple silicon — an adapter over `mse_vt_dec` (ffmpeg's hwaccel on native `vp9` SIGILLs). Session decoders take a stream only for an engine that sets `VpParams.hw_session` (file_av; MSE runs its own session). The session writes 8-bit NV12, so local VP9 profile 2 decodes in software on native `vp9`. MSE's own VP9 session gets a vpcC built from the keyframe header; VideoToolbox decodes 4:2:0 at 8 and 10 bits there (to 8-bit NV12) and refuses 4:2:2, 4:4:4 and 12-bit, which then go to vpipe.
- **Fallbacks and latches** — a software format from `get_format`, `ENOSYS`, a failed hardware or session open, or 3 hardware decode errors in a row latch the codec off the hardware for the stream and reopen in software. Before the first picture vpipe replays the packets itself; a keyframe that fails is resent to the new decoder; otherwise it returns **`VP_RESYNC`** and the engine feeds from a keyframe (MSE `vf_resync_key`, file_av `v_need_key`). A lost D3D11 device reopens in software without a latch. `vpipe_new_stream` (a new file, MSE `changeType`) clears the latches; Linux also keeps a codec the GPU rejected off for the process. A presenter change that flips the hardware decision reopens the decoder at the next keyframe sent. Software errors: MSE reopens on each; file_av reopens after 8 without a picture, and **`VP_DEAD`** after 2 such reopens — no decoder takes the stream, the reason is in `vpipe_failure`; file_av reports it as player error `E60021`, MSE logs it and stops video.

## Decoder capabilities (`mse_caps.c`)

The table YouTube's `navigator.mediaCapabilities.decodingInfo` and the MSE type checks answer from: one per process, rows of `{codec, max bit depth, widest chroma, max size (either orientation), max fps at that size, hw}`. `mse_host_create` starts the probe on its own thread; a query before it finishes gets `MSE_CAPS_PENDING`, so the QuickJS thread never waits.

- **Rows** — hardware: Windows `mse_d3d11_caps` (d3d11va hwaccel + DXVA profile + `GetVideoDecoderConfigCount` up a size ladder, 8-bit 4:2:0 only, dropped once the device is lost); Apple `vpipe_hw_vt_caps` (the same VideoToolbox gating vpipe and MSE's own sessions use; sizes are Apple silicon's, VT has no query); Linux `mse_hwdev_caps` (CUDA: `cuvidGetDecoderCaps` per codec and bit depth, resolved from libnvcuvid like ffnvcodec's loader, whose headers FFMPEG_ROOT lacks; Vulkan: the device's decode extensions, 8-bit up to 4096x2304; a codec the GPU later rejects drops out with it). Software: each bundled decoder present, with a pixel-rate budget per hardware thread (≤ 16) that only ever answers smooth.
- **Answer** — supported: a row takes codec, bit depth, chroma and size; smooth: one of those also covers `w*h*fps`; powerEfficient: a hardware one does. Audio codecs we decode are all three.
- **Playback quality** — `mse_host_video_quality` (`getVideoPlaybackQuality`): pictures shown, plus those dropped for missing their time — decoded more than 80 ms behind the clock, or a stale GOP skipped undecoded — on every video path (vpipe, Apple sessions, MediaCodec). A seek's or resume's run-up (`show_late`) is not a drop. Counts restart with each MseAv (`load()` / `src=`), as Chrome's do per load.
- **Android** — no probe: `MseHostNative.setDecoderCaps` (`mse_caps_set_rows`) fills the table from MediaCodecList; until then queries are `MSE_CAPS_NONE` and the player keeps its pre-table behaviour.

## Threads and locks (desktop)

- **vpipe**: open / close / flush / send / receive / new_stream from one thread at a time; set_presenter / present / flush_picture / frames from any.
- **MSE**: the QuickJS thread appends, seeks, rests and `changeType`s under `a->mu` (and `a->amu`); the video thread (`vid_loop` → `mse_av_pull_video`) opens the decoder lazily, sends / receives and picks a picture under `a->mu`, then shows it after unlocking, under `a->show_mu` (`v_epoch`, bumped when the decoder closes, drops a picture picked before); `dec_loop` is audio only.
- **file_av**: the Kotlin `player` thread runs every command and `file_av_step` — demux under `p->mu`, video open / close, and the due picture shown with `p->mu` dropped; `dec_loop` sends / receives without `p->mu` (`dec_busy` / `dec_epoch` keep seeks and rests off it) into a 4-picture ring; `a_loop` decodes audio.
- **Bind**: a binder runs under `DesktopVideoSurface.bindLock` (any thread, usually the EDT): `vpresent_bind` first, outside engine locks, then the engine's pointer swap (MSE under `h->av_mu`), then `vpresent_unbind` of the previous presenter.
- **Lock order**: MSE `h->mu` → `h->av_mu` → `a->mu` → `a->show_mu`; file_av `p->mu`; then the presenter's `present_mu` → `mu`, and `present_mu` → the D3D11 device lock. vpipe's mutex is a leaf. Kotlin: `bindLock` for the presenter's lifetime and binders, `frameLock` only for CPU frames — a binder can wait on an engine's video lock while that engine's thread is inside `onFrame`.
